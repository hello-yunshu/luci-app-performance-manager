# OpenWrt 四仓库统一分发、安装与更新：Goal 执行提示词

## 目标

完整收敛 `luci-app-performance-manager`（PM）、`luci-app-cloudflare-ip`（CFI）、`rill-openwrt-packages`（Rill Runtime）和 `yun-openwrt-packages`（统一 feed）四个 GitHub 仓库，交付可签名发布、可在设备上安装、可更新、可诊断的统一方案。明确支持 OpenWrt 24.10.8（IPK，旧稳定/EOL）和 25.12.6（APK，核验时当前稳定），架构聚焦主流设备而非覆盖全部官方 package architectures；所有被列为支持的版本 × 架构组合，都必须通过构建、依赖解析、安装/升级及相应运行验证。

最终让用户从一个可信 feed 安装和更新这几款软件；PM 只有一种面向用户的正式版本；PM 依赖共享的 Rill Runtime；CFI 无 Rill 时仍能正常运行，并可从界面一键安装、检查更新和更新可选 Runtime。PM 也提供 Runtime 状态检查、安装/修复和更新入口。不得在 PM、CFI 包里各自复制或私带第二份 Rill。

## 仓库范围

在本机分别检查并协同修改以下独立仓库；每个仓库单独维护提交边界、工作流、版本和发布物：

- `/Users/user/Documents/GitHub/luci-app-performance-manager`
- `/Users/user/Documents/GitHub/luci-app-cloudflare-ip`
- `/Users/user/Documents/GitHub/rill-openwrt-packages`
- `/Users/user/Documents/GitHub/yun-openwrt-packages`

它们当前已有用户和其他任务遗留的未提交修改。开始时逐仓库记录分支、HEAD、工作区差异和未跟踪文件；不得清理、覆盖、还原或夹带与本目标无关的更改。先读各仓库的 `AGENTS.md`、相关发布文档、工作流和包 Makefile。

## 已确定的产品决策

1. **PM 面向用户只发布一种正式安装形态**：一个完整的 LuCI/服务/脚本包（采用现有命名时优先 `luci-app-performance-manager-all`，但开始实施前核实现有包名、迁移兼容和 feed 能力，最后固定唯一公开包名）。移除“用户需要在多个 PM 变体间选择”的状态；旧拆分包提供安全迁移/冲突处理，不能留下两套服务或文件争抢。
2. **Rill 是 PM 的硬依赖、共享的独立包**。PM 包依赖与其兼容的 `rill-runtime-preview`（或经本轮验证后确定的唯一渠道包名）；Rill 由 Rill 仓库构建、签名和发布，统一 feed 引用其经资格验证的产物。PM 不内嵌 Runtime 二进制。CFI 将 Rill 视为可选能力。
3. 设备已有兼容 Preview Runtime 时，PM 安装/更新复用现有包，不重复安装或覆盖文件。已安装 Stable、未知来源或不兼容 Runtime 时，必须在执行前清楚说明冲突及影响，不能静默降级、覆盖或移除用户数据。Runtime 更新要考虑同机所有消费者，并保持包管理器拥有文件。
4. CFI 的 Runtime 管理在界面上提供一键安装、检查更新、更新以及必要的修复/错误反馈；Runtime 不存在时 CFI 主功能照常工作。PM 提供对应的 Runtime 状态检查、安装依赖修复和更新入口。所有动作都通过受控后端/RPC 与受信任的软件源和系统包管理器完成，不能让前端拼接任意 shell 命令。
5. 统一 feed 是面向用户的入口，纳入 PM、CFI、Rill 和现有 feed 收录应用。保留 Rill 仓库作为 Runtime 的唯一构建、资格验证和上游发布来源；避免双重发布、版本漂移、签名信任不一致。
6. 支持 OpenWrt 24.10 的最后有效维护版本和 OpenWrt 25.12 当前有效稳定版本。24.10 使用 IPK/opkg/usign 路径，25.12 使用 APK/apk-tools/签名索引路径；不得混用包格式、升级命令、索引或签名机制。

## 执行阶段

### 阶段 1：四仓库现状审计和兼容矩阵

- 核实官方 OpenWrt 版本状态、最新修订、SDK 可用性、目标/子目标及每个发布版本的 `package architecture` 列表；使用官方 OpenWrt 下载站、SDK/feeds 源码和本地仓库作为证据，记录核验日期和链接。核验基线当前为 24.10.8 和 25.12.6，今后版本更新以官方发布状态为准。
- 不把“Rust target 映射存在”误当成 Rill 已支持；逐个验证 SDK、Rust 标准库、C/系统依赖、工具链链接器、ELF ABI、内核依赖及运行环境。
- 建立一个机器可读的兼容矩阵作为构建/发布真源，字段至少包括 OpenWrt 版本、包格式、target/subtarget、package architecture、Rust target（若适用）、每个包是否构建/安装/运行合格、验证作业、排除理由。各仓库的 CI、feed 目录、安装器和文档由矩阵生成或校验，禁止互相矛盾的手写架构列表。
- 架构覆盖目标：以主流家用/软路由平台为首批范围，不要求覆盖全部官方 package architectures。重点核验 `x86_64`、`aarch64_generic`、`aarch64_cortex-a53`、`aarch64_cortex-a72`、`aarch64_cortex-a76`、`arm_cortex-a7_neon-vfpv4` 和 `mipsel_24kc`；只有 SDK、依赖、Rust/ELF ABI、安装升级和相应运行验证通过后，才能把某个包/版本/架构组合标为正式支持。若 MIPS 或其他个别架构暂时无法可靠资格验证，应保留 CFI noarch 可用的较宽覆盖，并单独标记 PM/Rill 不支持，写出证据和限制。
- 对不具备可靠 Rill 运行/构建验证的架构，明确拆分包能力：例如纯 LuCI/脚本型 CFI 和带原生 Rill 依赖的 PM 不必具有相同架构集合。不能让 feed 宣称某架构可安装 PM 却缺少可解析、ABI 兼容的 Rill 依赖。
- 24.10 在官方支持生命周期结束或接近结束时仍需实现用户要求的兼容构建，但文档明确其维护状态、停止安全更新的风险和支持边界；对 SDK/官方依赖已不可获得的组合提供具体说明，不做虚假兼容承诺。

### 阶段 2：包依赖、唯一 PM 形态和升级迁移

- 收敛 PM 包结构及 Makefile、`DEPENDS`、`CONFLICTS`、安装文件清单、菜单/RPC/ACL、卸载脚本、CI、README、中文/英文文档和发行说明，只留一个正式 PM 安装入口。
- 为旧拆分包与旧 all-in-one 包定义从现有状态升级到唯一包的安全路径。确认 opkg 和 apk 对替换/冲突/依赖的实际行为；必要时提供明确迁移指引或兼容迁移包，不能在升级中误删配置、数据库或用户数据。
- PM 对 Runtime 的包依赖必须反映真实要求；检查与 `rill-runtime-preview`、Stable Rill、旧 PM 包、CFI Runtime 管理功能之间的冲突和升级顺序。
- Rill 同一设备只允许一个包管理器拥有 `/usr/bin/rill-runtime` 及相关文件。检查 `opkg`/`apk` 文件归属、替换路径、卸载行为、版本 pin/compatibility manifest 和包签名。
- 按 24.10 和 25.12 分别验证从无 Rill、有兼容 Preview、有 Stable、有旧拆分 PM、从旧版本更新以及卸载/重装的场景。

### 阶段 3：CFI 与 PM 一键安装/更新体验

- 审计现有 LuCI 页面、rpcd ACL、后端实现和包管理器调用，规划并实现状态展示：已安装且兼容、可更新、未安装、版本不兼容、来源不受支持、安装/更新失败及可恢复状态。
- CFI 环境检测只列出实际检测到的代理软件；没有任何支持的软件时显示一次未检测到提示。该既有需求若尚未正确落地，应一并保留并核实。
- 安装/更新按钮要有明确的进度、成功/失败结果和错误诊断；防止重复点击并发、部分安装、包数据库锁冲突及刷新页面造成状态错乱。按包格式调用正确系统包管理器。
- 仅使用 HTTPS 和经过设备信任密钥验证的软件源/签名索引；禁止 `curl | sh` 或绕过包签名校验。若用户已有非本 feed 来源的同名 Runtime，先准确识别包归属和版本，再提供可理解的选择/修复路径。
- 更新共享 Runtime 前，检查兼容性清单中已安装的 PM/CFI 消费者；只有目标版本满足所有已安装消费者约束才更新。更新失败时保留可诊断状态并尽可能安全恢复。
- 对每个界面文案补齐中英文翻译；RPC 输入校验最小权限，shell 参数安全引用，校验 URL/版本/架构不可由请求端任意覆盖。

### 阶段 4：统一 feed 与版本/架构发布

- 扩展 `yun-openwrt-packages`，对 24.10 IPK 和 25.12 APK 建立清晰、稳定、互不混淆的版本 × 架构路径与安装说明；保留现有包并纳入 PM、CFI、Rill，避免把兼容薄封装重复当作独立 Runtime 发布。
- 决定统一 feed 的签名和信任策略：24.10 包及索引的 usign 信任链、25.12 APK 包/`packages.adb` 的信任链、密钥轮换与撤销说明必须可验证。私钥只保存在 CI Secret；不复制明文私钥，不在构建日志中打印。
- `yun-openwrt-packages` 通过锁定来源仓库、不可变 commit/tag、包版本、构建来源与哈希来复现构建；Rill 二进制消费必须来自特定成功资格作业的不可变产物，不得下载“latest”或无校验二进制。
- 同步 feed 的机器可读 catalog/manifest、GitHub Pages 发布目录、README、设备端安装命令和 UI 源配置。明确首次信任公钥的安全路径、安装、刷新、更新、卸载、回滚/故障恢复方式。
- 检查包元数据依赖与官方源分工；确保每个矩阵格中所有硬依赖可从该版本官方 feeds 或统一 feed 解析，不遗漏 LuCI、ucode、libc、系统工具或原生库依赖。

### 阶段 5：端到端验证与发布收口

- 每个声明支持的版本 × 架构都必须：构建成功；包格式与 package architecture 正确；签名和索引校验成功；依赖可解析；在干净根文件系统中安装成功；核心服务/RPC/LuCI 可启动；升级和卸载不破坏配置/用户数据。
- 为全量架构运行可自动化的 SDK 构建、元数据、依赖、签名、安装和 ABI/ELF 检查。选择每种 CPU/ABI 家族的真实设备或官方镜像做运行验证；不能仅以 x86 模拟结果推断其他架构运行无误。
- 对 Rill 强制执行真实目标 ELF、动态库、musl ABI、权限、启动、健康检查和与 PM 版本协议一致性的检查。缺少实机时标为 build/install qualified，不标为 device runtime qualified。
- 验证 opkg → 目标 IPK feed、apk → 目标 APK feed 两条完整路径，包括 feed 首次配置、导入公钥、更新索引、一键安装、检查更新、更新和错误/签名拒绝。
- 做真实 LuCI/RPC/ACL 链路检查，覆盖权限不足、后台未运行、包锁定、网络不可达、签名错误、已安装兼容 Runtime、Stable/未知 Runtime 冲突、架构不支持和回滚。
- 不因测试通过而忽略失败；修复后重跑相关矩阵。除非确有客观环境限制并记录证据，不得把未执行的验证写成通过。
- 更新四仓库 README、兼容矩阵、支持/不支持架构说明、依赖/迁移指南、维护状态、故障排查、CHANGELOG/Release notes；四个仓库版本和安装文档互相一致。
- 最终逐仓库汇报：改动文件、版本变化、兼容矩阵、发布产物位置、CI/设备验证结果、仍未验证的组合和原因、潜在升级风险。保持各仓库修改可审查；不要擅自发布正式 Release 或推送远端，除非本 Goal 的明确范围/仓库规则允许。

## 完成标准

- 四个仓库的包定义、构建、签名、发布和安装说明构成可复现的一条链。
- 24.10/IPK 与 25.12/APK 的实际有效支持版本已核实，并在兼容矩阵中清楚列出。
- 架构覆盖以官方目标清单和逐架构证据为基础，首批聚焦主流 x86、ARM64、ARMv7 与 MIPS 平台；每个未支持项都有明确、可验证的原因，且 CFI、PM、Rill 分别列出真实能力边界。
- PM 只保留一个正式用户版本，依赖唯一、共享、外部签名发布的兼容 Rill Runtime；旧包迁移路径已验证。
- CFI 不依赖 Rill 才能工作；CFI 与 PM 均具有可信的一键安装/检查更新/更新体验，且共享 Runtime 更新受所有消费者兼容约束保护。
- 统一 feed 能按 OpenWrt 版本和设备架构提供正确格式、可信签名和可解析依赖的包。
- 所有实际验证结果、失败、限制和支持边界都有证据记录；不把 build-only 验证描述成完整设备支持。

## 执行方式

先完成四仓库审计、兼容矩阵和风险清单，再连续推进实施与验证，直到达到完成标准。遇到可由代码、现有产品决策或官方证据解决的问题，自行判断并继续；仅在会改变产品行为且无法从既有讨论推断时，才提出具体问题。不得停在建议、计划或部分实现。
